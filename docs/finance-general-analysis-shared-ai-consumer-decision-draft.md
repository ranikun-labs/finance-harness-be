# Finance General Analysis ↔ Shared AI Consumer Decision Draft

**Status:** Finance-owned typed adapter, strict v1 HTTP/JSON consumer, and fail-closed result mapper are implemented for local/test only. The outbound bean requires both `!prod & !production & (local | test)` and explicit `finance.shared-ai.enabled=true`; the local default is off. The client accepts loopback URLs only and rejects URI userinfo. Fake loopback server tests exercise the consumer contract; this is not proof of a connected Shared AI service or approval for production transport/auth. Persistent state remains out of scope.

## Finance-owned contract in this BE

`GeneralAnalysisExecutionPort.execute` accepts `GeneralAnalysisExecutionInput(question, checkedItemIds, lens)` and returns either `Success(GeneralAnalysisCandidate)` or `TechnicalFailure`. The candidate is structured as `summary`, `observations`, `assumptions`, `nextChecks`, and `evidenceNote`.

`GeneralAnalysisApplicationService` resolves the owner through `CurrentUserPort`, verifies that the Checklist is confirmed and belongs to the Question, applies Finance policy before Lens routing, then calls the Finance execution port. It validates a successful candidate before exposing it. A non-safe policy classification blocks execution. This runtime remains limited to `!prod & !production & (local | test)` and uses process-local storage.

`FinanceGeneralAnalysisExecutionAdapter` implements `GeneralAnalysisExecutionPort` behind a Finance-owned typed `FinanceSharedAiPort`. The opt-in `FinanceSharedAiHttpClient` maps that port to `POST /internal/shared-ai/v1/executions` using the agreed local/test JSON contract. It builds `FinanceGeneralAnalysisBusinessInput(question, checkedChecklistItemIds, lensRef)`, uses `finance.general-analysis@1`, and formats a deterministic plain-text query for the Shared AI `query` field. Its Finance request context is a product-owned seed: product, tenant, exact verified Question/Checklist resources, CurrentUserPort principal, analysis request ID, and optional correlation/authority refs. It contains neither `executionReference` nor `contextVersion`; Shared AI owns both. The only Spring context factory is `LocalFinanceExecutionContextFactory`, enabled with the opt-in local/test bean and an explicit tenant property; no production implementation or bean is registered. The application passes only the current owner, verified Question/Checklist IDs, and Finance-generated analysis request ID to the factory. Before invocation it rejects mismatched principal/resource/request refs, blank tenant, and blank optional refs.

On success the adapter independently checks the Shared-issued execution reference and context version (`1` for the aligned local contract), all echoed product/tenant/resource/principal/request/correlation/authority refs, evidence identity, source refs, and non-widened resource scope before parsing. It parses only the existing Finance candidate fields (`summary`, `observations`, `assumptions`, `nextChecks`, `evidenceNote`) from the Shared interpretation string, rejecting malformed, blank, duplicate-key, trailing-content, missing-field, and extra-field outputs. `GeneralAnalysisApplicationService` then runs the existing `FinanceGeneralAnalysisOutputValidator` before it stores or exposes the candidate. Shared technical failures and every mismatch/parser failure become Finance `FAILED` with no output. Repeated requests invoke the port again; there is no retry or deduplication guarantee.

The BE includes `src/test/resources/finance-general-analysis-consumer-fixture.json` and Finance-side logical consumer tests. The v2 JSON resource is byte-identical to the fixture in the Shared AI repository and is used only for deterministic tests. It contains synthetic product/tenant/resource/principal/request/correlation/authority seed refs, has no caller-issued execution ref or context version, and carries `sharedAiQuery` only for comparison. The Finance fixture consumer models Shared AI issuing execution ref and context version in the result. None of these fixture values are used by the operating formatter or port.

The fixture's tenant, principal, product, resource, request, correlation, and authority references are synthetic values. The fixture omits execution and context-version refs because Shared AI owns those result fields. The adapter checks the principal against the verified CurrentUserPort owner, checks resource refs against the verified Question and Checklist, and rejects a blank tenant. In this local/test slice the tenant comes only from explicit `finance.shared-ai.tenant-reference` configuration; the repository's `CurrentUserPort` exposes only an `IdentityUserId`, and there is no trusted production tenant source. No production context is synthesized from fixture values. The HTTP client is loopback-only; its fake-server tests do not prove service connectivity.

The consumer request contains exactly `context` (scope and principal/request/optional correlation/authority refs), `skillId`, and opaque `query`; it never sends execution or context-version fields. Success maps the full evidence context/items plus warnings and nullable usage into Finance-owned types. Shared technical failure, non-200 status, timeout/network errors, malformed JSON, unexpected fields, or invalid evidence map to a Finance failure with no candidate output. The client uses a 1-second connect timeout and 5-second request timeout, follows no redirects, and does not retry. A repeated application call submits a new execution.

Finance currently enforces the local/test usage shape as nullable nonnegative integer `inputTokens`, `outputTokens`, and `totalTokens`; a negative count makes the response malformed and keeps the candidate hidden. Shared AI should publish or confirm this constraint in its v1 contract.

To bound the opt-in local/test consumer, Finance rejects response bodies above 1 MiB, more than 128 evidence items, more than 64 warnings, or more than 128 resource/source references in a single array. These Finance-side limits accept the current two-evidence-item/one-warning fixture and are consumer safeguards, not additions to the Shared AI wire schema. Over-limit responses fail closed without exposing interpretation text.

## Shared AI contract inspected

Historical contract inspection: `shared-ai-finance-consumer/platform-core/shared-ai`, branch `codex/rpl126-finance-consumer`, commit `d67dd594bfe19b1076dc7ee90669b35d75d492cb`. Shared AI baseline reviewed for this decision: E commit `6d81412` (a historical snapshot, not a claim about the final/current E HEAD).

- `SharedAiExecutionService.execute` accepts `ExecutionCommand(context, skillId, query)` and routes through `SkillRegistry` to a `SkillHandler`.
- `ExecutionContext` requires an `ExecutionScope` with `productReference`, `tenantReference`, and `resourceReferences`, plus `principalReference`, `requestReference`, `executionReference`, and nullable `correlationReference`.
- Shared `ExecutionResult.Success` contains an `interpretation` string, `Evidence` envelope, warnings, and optional model usage. `TechnicalFailure` contains one of `UNSUPPORTED_SKILL`, `PRODUCT_TOOL_FAILURE`, `RETRIEVER_FAILURE`, `MODEL_FAILURE`, or `CORRELATION_FAILURE`.
- The service validates the result execution reference, evidence context, and nonblank interpretation. It does not apply Finance policy or interpret Finance candidate sections.
- At historical commit `d67dd59`, the only production handler found was `ReviewKnowledgeSkillHandler`, registered as `review-knowledge`.
- At the reviewed E snapshot `6d81412`, a distinct `FinanceGeneralAnalysisSkillHandler` was registered as `finance.general-analysis@1`. It consumes the existing `ExecutionCommand(context, skillId, query)` with the query opaque, and returns the existing Shared AI Success/TechnicalFailure and generic Evidence results. It does not own Finance context construction, PolicyGuard, candidate parsing, or output validation. This records the reviewed baseline only, not the final/current E HEAD.
- The aligned seed contract makes Finance supply only product/tenant/resources/principal/request plus optional correlation/authority. Shared AI issues `executionReference`, sets its own `contextVersion` (`1` in the reviewed local contract), and returns the complete context through `Success.evidence.context`; `Success.executionReference` must match it. Finance mirrors this shape in Finance-owned types only. The HTTP JSON form is a local/test consumer contract, not a canonical production API.
- `SharedAiExecutionService` is an in-process service. Finance has a local/test HTTP client, but these repositories have not verified an operating service endpoint or an authenticated production bridge.

## What the bilateral fixture covers and what remains blocked

The Finance BE build has no dependency on the Shared AI module, and the Shared AI source is in a separate repository. The bilateral tests independently load the same test resource; the Shared test maps it to real Shared AI types while the Finance test maps Finance input to the logical fixture shape. Finance now has a loopback-only HTTP implementation of its typed port; it does not bridge directly to `SharedAiExecutionService`, and the fake-server tests do not establish a connected service integration.

The fixture and fake-server tests do not resolve the remaining runtime integration decisions; the reviewed Shared AI registration snapshot is listed for context:

1. **Skill registration versus operating connection:** The reviewed Shared AI snapshot `6d81412` registered the distinct `finance.general-analysis@1` handler. Finance's loopback-only consumer can target the agreed v1 route, but there is no verified operating Shared AI HTTP endpoint or production connection.
2. **Execution context trust:** Finance has `CurrentUserPort` and an owner-scoped local identity. Finance constructs product, tenant, resource, principal, request, and optional correlation/authority seed refs; Shared AI issues execution and context-version refs. Finance validates the returned context against its seed and checks evidence refs before parsing. The opt-in local/test factory reads tenant only from explicit configuration; `CurrentUserPort` has no tenant value. A trusted production tenant source and its lifecycle remain unresolved; authority refs must come from trusted Product context only when a protected action requires them.
3. **Query construction:** Finance now has a deterministic plain-text formatter for the existing Shared AI `query` field. The JSON query string in the bilateral fixture is not used for an operating request. Query size limits, escaping behavior for adversarial user text, and prompt versioning still need an approved runtime policy.
4. **Evidence and candidate mapping:** Finance checks the Shared success execution ref and evidence envelope context, item refs, IDs, sources, and resource scope. It strictly parses the existing candidate field shape from `interpretation`, and the application `OutputValidator` is the final exposure gate. The mapping is implemented locally, but a connected Shared AI handler/output prompt and operational evidence-source semantics still need owner review; the handler must return the exact Finance candidate JSON shape in `interpretation` for this parser to accept it.
5. **Correlation lifecycle:** The fixture proves exact reference equality for synthetic values only. The Finance analysis ID and the production Shared request/execution/correlation reference lifecycle have not been mapped.
6. **HTTP/auth boundary:** The path and JSON fields are implemented as a local/test contract only, restricted to loopback with no credentials. Production endpoint discovery, F5 route, service identity, authentication, authorization, and a canonical transport contract remain unresolved.
7. **Timeout/cancel/concurrency:** The Finance consumer applies 1-second connect and 5-second request timeouts and has no retry. Cancellation propagation and duplicate-in-flight behavior remain unresolved; Finance has no cancel command or concurrent-request contract.
8. **Retry/dedup:** The Shared service invokes the selected handler once per `execute` call and does not add retry or duplicate suppression; its current contract test verifies repeated commands call every port again. Finance likewise executes repeated analysis requests again and has no request idempotency key. No retry or deduplication guarantee may be claimed for a consumer adapter.
9. **Persistence:** Finance Question, Checklist, and Analysis state is process-local and disappears with a fresh process. No Shared result or Review persistence contract exists in this BE. Any durable lifecycle, retention, deletion, or Journal reference requires separate approval.

The typed Finance port has a loopback-only local/test HTTP implementation behind opt-in Spring wiring. No result, query, or context fixture claims production connectivity.

## Decisions needed before a real consumer integration

- Provide a trusted tenant/context factory based on authenticated CurrentUserPort state and Finance-owned Question/Checklist ownership checks. The adapter intentionally has no default tenant or production context provider.
- Provide a verified operating Shared AI service endpoint and production service-auth protocol. The local/test loopback consumer deliberately has no remote URL or credentials.
- Review the Finance plain-text query formatter and the candidate-shaped JSON interpretation prompt, including escaping/size limits and evidence note semantics.
- Freeze evidence-source semantics and warning handling. Finance currently accepts only evidence envelope references that match the Finance request context and resource scope.
- Decide timeout, cancellation, in-flight concurrency, and whether a future Finance request key is required; do not infer retries or deduplication from the Shared service.
- Resolve the production endpoint and identity trust protocol independently of the local/test consumer seam.

Production HTTP/auth, cancel/concurrency, and persistence remain on hold. No retry or durable idempotency guarantee is claimed; repeated calls execute again. Finance Question, Checklist, and Analysis state remains process-local and disappears with a fresh process. No schema, Review entity, or durable result lifecycle is authorized.

Until the unresolved production decisions are made, the Finance v1 consumer and its logical fixture remain local/test-only evidence, not a working production integration. The separate Stored Journal Review contract draft remains draft-only and does not expand the local/test-only runtime or persistence boundary.
